## 一、铁律：文案字段的硬约束（来自校验工具，违反即 fail）

`tools/equipment_copy_quality_check.gd` / `designed_enemy_copy_quality_check.gd` / `run_copy_quality_check.gd` / `ui_copy_quality_check.gd` 对写进代码的文案强制：

1. **必须含中文（CJK）**，且 **name 与 description 都不能为空**。
2. **禁止任何英文字母**（a–z / A–Z）。`docs/lore` 样例里出现的英文（家族键 `mining_barrage`、`colossus`，或 `run/drone/dash` 等）**只是文档索引，写回时必须全部去掉/改中文**。
3. **禁设计词**（`FORBIDDEN_COPY_TERMS`）：`适合 / 预留 / 测试 / 构筑 / 需求 / 玩家 / build / early / late / run / drone / dash / fire`。
   - 特别注意「**玩家**」被禁——正文一律用「你」。
   - 「构筑 / 需求」被禁——描述装备别用这两个词。
4. 写文案时**保持专有名词与正典完全一致**（席位名、亚种名、星髓矿、算力、天穹协议、方舟核心、引导之声、回声…）。

> 每改完一族/一批，立刻跑对应 check（见第四节），**红了当场修**，不要攒到最后。

## 三、需要先决策的结构性问题（不是纯文本替换）

这两项动到数据结构，**先决定再动手**（可回报给项目负责人，或按建议默认执行）：

1. **`06` 敌人图鉴档案往哪写？**
   - 现状：`DesignedEnemyCatalog.gd` 每条只有 `mechanic`（打法手感），且 check 只验这个字段。`06` 写的是"它曾经是什么"的世界观档案，**当前无字段容身**。
   - 建议：给每条加一个 `codex`（或 `flavor`）字段承载 `06` 的档案文本，并在 `designed_enemy_copy_quality_check.gd` 增加对该字段的同规则校验；`mechanic` 保持不动（它是打法说明，本就该和世界观分开）。
   - 若不想动结构：`06` 暂留作文档，代码侧只需确认 25 条 `mechanic` 不与新正典冲突（现有 mechanic 是中性战斗描述，基本无需改）。

2. **`03` Boss 台词怎么进游戏？**
   - 现状：boss 脚本只有 `boss_name` 和进场黑幕白字（只显示名字）。登场/半血/击败台词**没有字段、也没有播放时机**。
   - 建议：在 boss 基类/各控制器加 `intro_line` / `half_hp_line` / `defeat_line` 三个 `@export`，并在进场结束、半血、`_die()` 时触发一个简单的台词浮层（可复用现有 `_setup_intro_overlay` 那套 CanvasLayer）。文案照 `03` 填。
   - 这是有工作量的功能开发，建议**单独排期**，别和纯文本替换混在一起。

> 结论：**先做纯文本替换（05 / 07 / 04 / 02）**——这些字段都已存在，改完就能过 check、直接见效；**06 / 03 涉及加字段/加系统，单独处理**。
